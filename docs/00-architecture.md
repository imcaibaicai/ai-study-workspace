# 架构总纲：四级渐进披露

> 这套工作区要解决的问题只有一个：**让 AI 在长期、跨会话的项目里，始终知道"现在该看哪几个文件"，而不是每次都把整个资料库灌进上下文。**

---

## 一、为什么需要架构

把一堆资料丢给 AI，短期能跑，长期必崩。崩溃点有三个：

| 崩溃点 | 现象 | 后果 |
| :--- | :--- | :--- |
| **上下文膨胀** | 每次会话都全量读资料 | token 成本线性增长，首字延迟（TTFT）上升 |
| **注意力稀释** | 关键约束淹没在无关内容里 | 模型遵守规则的稳定性下降，规则"读了但不执行" |
| **跨会话失忆** | 新会话不知道上次做到哪 | 反复确认进度，重复劳动 |

四级渐进披露的应对是：**把"读什么"从模型自由裁量，变成按层级查表**。

---

## 二、四个层级

```text
┌────────────────────────────────────────────────────────┐
│  L0  入口层    AGENTS.md                                │
│  首屏极简指针 + 启动序列 + 不可动摇的硬约束                │
│  预算：≤ 90 行                                          │
└──────────────────────────┬─────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────┐
│  L1  状态与调度层    状态中枢 JSON + ROUTER.md            │
│  当前进度/掌握矩阵 + 意图→时机→文件 路由表                │
└──────────────────────────┬─────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────┐
│  L2  规则与底座层    协作协议 + 运行规则/                  │
│  交互纪律 + 工程避坑账本 + 新建文件规范                    │
└──────────────────────────┬─────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────┐
│  L3  领域层          资料库/{领域}/                       │
│  计划 → 考点 → 题型模板（按需创建，逐层下沉）              │
└────────────────────────────────────────────────────────┘
```

### L0 入口层

Agent 每次进入工作区**自动发现**的第一个文件。只放三样东西：

1. **环境基线**：这台机器上什么是真的（Python 版本、没有 Pandoc、路径含空格）
2. **启动序列**：按什么顺序读文件
3. **硬约束**：编号制的铁律，每条一句话

**关键纪律：≤ 90 行。** 超了就下沉到 L2。这个数字不是玄学——它是"每次会话都要付一次的固定 token 税"，越短越好。

### L1 状态与调度层

**状态中枢**解决跨会话失忆：把"现在在哪"从对话历史里剥离，落到一个结构化 JSON。

**路由矩阵**解决"该读什么"：不是文件清单，而是**意图 → 触发时机 → 文件**的三维映射。

### L2 规则与底座层

协作协议定义"怎么交互"，避坑账本记录"踩过什么坑"。这一层按需查阅，不强制全读。

### L3 领域层

具体领域的资料。按 `计划 → 考点 → 题型` 三层下沉，每层只在需要时展开。

## 三、两种互联机制

光有层级是不够的——层级是树，树会走到死胡同。所以需要两个方向相反的机制：

### 1. 中枢路由表（Top-Down）

由 `ROUTER.md` 统一维护：**用户说了什么 → 该读哪几个文件**。

### 2. 文尾网状辐射（Bottom-Up & Lateral）

**每一个 Markdown 文件文尾**都挂一张《关联文件与引用时机网格》，写明：

| 列 | 含义 |
| :--- | :--- |
| 目标文件相对路径 | 去哪 |
| 核心内容 | 那是什么 |
| **引用时机与触发条件** | **什么时候该去** |
| 关联类型 | 上游总纲 / 前置考点 / 下游模板 / 状态中枢 |

第三条是灵魂：它不只说"有什么"，还说**"什么时候不该读"**。

两者合起来，任意打开一个文件都能沿网格继续走，形成**图而非树**。

## 五、这套架构不负责什么

诚实地划清边界：

- **不提供学科知识**。它只管"知识怎么组织、什么时候加载"，不管"这道题怎么算"。
- **不保证模型遵守规则**。硬约束是提示词，模型仍可能违反。真正可靠的是**校验器**（见 [03-file-protocol.md](03-file-protocol.md)）。
- **不适合一次性任务**。为长期项目设计，开销在"建立和维护结构"，短任务用不上。
- **层级数不是教条**。四层是经验值；领域多就加层，项目小就砍到两层。
